# 模型推理分析：从配置到实验结论

接手一个陌生模型，或者评审一项推理优化时，需要交付一份能支持工程决策的分析结论。单纯填满表格没有用。结论至少要回答：模型怎样计算，请求状态怎样增长，资源花在哪里，当前工作负载受什么限制，以及准备验证哪项改动。

这份方法适合直接用于模型接入、容量评审和优化方案评审。没有真实项目可分析时，可以先完成[结业案例](capstone.md)，再用同样的方法分析自己维护的模型。

## 1. 一份合格的分析应包含什么

建议把结果控制在一页正文和必要的附录内。正文保留五项内容：

1. 模型与运行时的确切版本。
2. 从输入到 Logits 的主数据流，以及 Decoder Layer 的结构。
3. 权重、请求状态和主要计算量的数量级。
4. 线上请求分布、SLO 和已经观察到的瓶颈。
5. 一项可验证的优化假设，包括收益、代价和回退条件。

这五项分别检验课程中的五种能力：读配置、还原计算、估算资源、理解工作负载、设计实验。缺少其中任何一项，优化结论都可能建立在错误对象或错误口径上。

## 2. 固定分析对象

先记录能够重新找到同一份模型和实现的信息。模型名称和 `latest` 标签不够精确。

| 必须记录 | 证据来源 | 为什么需要 |
| --- | --- | --- |
| 模型仓库与 revision | 模型仓库 commit | 配置和权重会更新 |
| runtime、镜像与 revision | 镜像摘要、包版本或源码 commit | Kernel、Cache 布局和并行实现属于 runtime |
| 权重保存 dtype、计算 dtype | Safetensors 元数据、启动参数、Profile | 文件大小不能直接推出计算路径 |
| 硬件与互联 | GPU 型号、卡数、NVLink/PCIe/网络拓扑 | TP、EP 和 Kernel 收益依赖硬件 |

找不到证据的字段直接写“待核对”。不要用模型名称、参数规模或经验值补空白。

## 3. 从配置还原模型

先画出一条主数据流，不必把每个算子都塞进图里：

```text
消息或多模态输入
→ Chat Template 与 Tokenizer / 视觉编码
→ [B,T,H]
→ 多层 Decoder
→ 最终归一化与 LM Head
→ [B,V] Logits
→ 采样或贪心选择
```

然后从 `config.json` 和固定版本源码中回答下面的问题：

```text
总层数、Hidden Size 和词表大小是多少？
每层使用哪一种 Token Mixer，层排列是否混合？
FFN 是 Dense 还是 MoE？Intermediate Size、Expert 数和 Top-K 是多少？
Attention 有多少 Query 头和 K/V 头？Head Dimension 是多少？
位置编码作用于哪些维度？
输入和输出是否共享 Embedding 权重？
```

配置只能说明声明值。遇到额外门控、部分 RoPE、K/V 头复制、混合层排列或特殊 Cache，继续查看模型前向和 runtime 实现。课程第 8 课给出了 Qwen3.5 的完整示例。

## 4. 建立资源账单

资源估算要分开统计不同对象，不能只报“模型占了多少显存”。

| 对象 | 至少计算什么 | 这个数字支持什么判断 |
| --- | --- | --- |
| 模型权重 | 精确参数量与保存 dtype 的有效载荷 | 单卡能否容纳、量化的容量上限 |
| Full Attention 状态 | 每缓存位置的 KV 字节、目标上下文和并发总量 | 长上下文容量、KV 量化和 Prefix Cache |
| 线性 Attention / SSM 状态 | 单请求固定状态和保存 dtype | 并发容量、状态复制与恢复 |
| 临时激活与 Workspace | 目标 Batch 和长度下的峰值 | 部署余量、OOM 与算子融合 |
| 主要 Linear FLOPs | Prefill 和单 token Decode 的近似量 | Dense/MoE 计算规模、量化假设 |
| Attention 长度项 | 不同上下文长度下的计算和读写 | 长 Prompt、长 Decode 的变化趋势 |
| 多卡通信 | Collective 类型、消息大小和次数 | TP/PP/EP 是否可能受通信限制 |

公式算出的是逻辑有效载荷或计算量。进程显存还包含分页、对齐、复制、通信 Buffer、CUDA Graph、Kernel Workspace 和内存池；最终容量要用目标 runtime 的实际峰值验证。

## 5. 把工作负载放进分析

同一个模型在短 Prompt、高并发服务和长上下文、低并发服务中，瓶颈可能完全不同。至少记录：

```text
Prompt 和 Output 长度分布
文字、图片和视频比例
精确共享前缀的比例与长度
到达率、并发和 Batch 策略
采样设置与质量检查集
TTFT、TPOT/ITL 的计时边界
`goodput` 使用的 SLO
```

只给平均长度会隐藏长尾。只给离线 token/s 也无法说明线上排队和 P99 是否达标。

## 6. 把优化写成可验证的假设

“开启量化”“增大 TP”或“使用 FlashAttention”都不是完整方案。先写清改动对象和成功条件：

```text
观察：哪一个端到端指标没有达标？
证据：Profile、容量计算或分桶数据指向哪一段？
改动：准备改变哪段计算、哪份数据或哪条调度规则？
上限：理论上能少算、少搬、少存或少等待多少？
代价：会增加哪些计算、通信、Cache、排队或质量风险？
实验：哪些条件保持不变，比较哪些端到端指标？
决策：达到什么阈值上线，什么情况回退？
```

例如，P99 TTFT 超标且多数请求共享长而精确的系统前缀，可以形成“Prefix Cache 减少重复 Prefill”的假设。它仍需验证真实命中 token 数、未命中路径、驱逐率、状态恢复正确性和同 SLO `goodput`，不能从开关状态直接推出收益。

## 8. 怎样判断分析已经完成

提交前逐项检查：

- 图中的每条支路都能在配置或源码中找到依据。
- 每个容量数字都能从 shape、dtype 和并发重新计算。
- 估算值、Profile 结果和端到端实测已经分开标注。
- 基线与实验组使用相同的请求分布、硬件和统计口径。
- 结论只覆盖证据能够证明的范围。
- 另一名工程师拿到 revision、参数和命令后可以复现结果。

如果现有证据只证明一个 Kernel 更快，结论就写“这个 Kernel 更快”。端到端收益、容量变化和质量结果必须分别验证。
